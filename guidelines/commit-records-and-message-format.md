# 提交信息格式规范

> **TL;DR**
> - **用途**：统一提交标题、正文和协作署名的写法。
> - **适用场景**：编写或审查 Git 提交信息。
> - **关键结论**：一次提交一个目的；标题清楚说明结果；正文按需补充原因和验证；提交前核对文件范围。

## 1. 标题格式

推荐使用：

```text
<type>(<optional-scope>): <中文结果描述>
```

示例：

```text
feat(plugin): 支持新的处理能力
fix(report): 修复失败状态的数据展示
perf(parser): 减少重复计算
refactor(core): 统一数据处理入口
docs: 补充使用说明
```

没有自然 scope 时省略括号：

```text
<type>: <中文结果描述>
```

也可以直接使用中文描述，但必须单一目的、结果明确：

```text
完善错误状态处理
整理文档索引
```

避免只有“更新”“修改”“优化代码”等无法判断实际内容的标题。

## 2. 常用类型

| 类型 | 适用情况 |
| --- | --- |
| `feat` | 新能力或新输出 |
| `fix` | 错误行为、边界条件或回归修复 |
| `perf` | 有测量依据的性能改进 |
| `refactor` | 不改变外部行为的结构调整 |
| `docs` | 文档新增或修改 |
| `test` | 测试设施或测试契约 |
| `chore` | 其他工程维护 |
| `merge` | 分支合并 |

scope 应使用稳定、短小的模块名；不要为生造 scope 增加无意义层级。

## 3. 正文与协作署名

完整格式：

```text
<type>(<optional-scope>): <中文结果描述>

<可选正文：为什么修改、关键口径、验证结果或已知限制>

Co-Authored-By: <协作方名称> <协作方邮箱>
```

正文规则：

- 简单且标题已表达完整的提交可以省略正文。
- 复杂修改应说明原因，而不是复述代码差异。
- 性能改进可记录前后测量条件与结果。
- 验证证据应区分自动化测试、编译和人工验收；未执行的项目不要声称已通过。
- 协作署名放在正文末尾，保留 `Co-Authored-By` 的精确拼写。

## 4. 提交粒度与范围

1. 一次提交只包含一个可审查目的，不混入无关重构、实验功能或文档。
2. 只暂存本任务文件，不把他人的修改或未完成的修改一并提交。
3. 提交前检查暂存文件、空白错误和实际差异。
4. 本地提交与远端推送是两个独立决定；推送前确认目标仓库、分支和公开范围。
5. 文档或代码包含项目名称、路径、邮箱、内部链接、提交哈希、业务数据等背景信息时，公开前必须脱敏。

## 5. 检查命令

```bash
# 查看暂存文件
git diff --cached --name-only

# 检查空白错误
git diff --cached --check

# 查看暂存差异
git diff --cached

# 查看提交标题和作者
git log --format='%h %ad %an %s' --date=short
```

以上规范只约束新提交，不要求为了统一格式而重写既有历史。
