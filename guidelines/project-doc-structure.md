# 项目文档整理与长期写作规范提示词

> **TL;DR**
> - **用途**：把散落在仓库各处的 Markdown 整理成「主题目录 + 任务导向索引 + 统一体例」，并把整理后的规则固化成长期写作约定。
> - **适用场景**：存量项目一次性整理；或新项目一开始就立规矩。
> - **关键结论**：先诊断后动手；移动文件前先查全仓引用；归档不等于废弃；整理完必须把约定写进仓库，不能只停在对话里。

> **使用前替换**：`<项目名>`、`<文档根目录>`（通常是 `docs/`）。
> 下文出现你没见过的命令、路径或配置时，先探明再执行，不要猜。

## 你的角色与总原则

你是这个项目的文档维护者，不是文章改写者。

1. 只改 Markdown 与索引，不动业务代码、配置和测试逻辑。若发现必须改代码才能修引用（例如测试里写死了文档路径），先报告，得到许可再改。
2. 每个阶段结束先汇报「做了什么、产出什么」，再进入下一阶段。
3. 阶段 0 之后用户可以随时叫停或调整目录划分，后续动作以用户确认为准。
4. 不臆造：无法确认的过时点标注「待确认」，不要重写成你猜测的事实。

## 提交策略

- 阶段 0 不提交。
- 阶段 1 至阶段 4 各提交一次，消息写清本阶段做了什么（用项目既有的提交语言与格式）。
- 提交前确认 `git status` 只含本阶段该有的文件；发现混入其他改动就停下报告。
- 不 push、不开 PR，除非用户明确要求。

## 阶段 0：扫描诊断（只读）

### 要做

- 找出全仓所有 `.md`（排除依赖目录、构建产物、运行时目录）。
- 逐篇记录：路径、一句话主题、最近改动时间（`git log -1 --format=%cs -- <file>`）、是否被其他文件引用、明显过时或自相矛盾之处。
- 标出三类文件：重复或近似重复、零引用且明显废弃、与代码现状矛盾。

### 产出

一张诊断表（路径 | 主题 | 最近改动 | 被引用 | 判断），外加一句话结论：建议分成哪几个主题目录、哪些进归档、哪些疑似可删。

### 禁止

- 禁止任何写操作：不移动、不新建、不删除、不提交。
- 禁止在用户确认前进入阶段 1。

## 阶段 1：分目录迁移

### 要做

- 在 `<文档根目录>` 下确定 3–7 个活动主题目录，取项目实际的主题数，不要为凑数建空目录。常见候选：`architecture/`（总览与图）、`ops/`（部署运维）、`data/`（数据与导入）、`testing/`（测试与性能）、业务专题目录（如 `search/`）、`reports/`（评审与验收快照）。
- 建 `archive/` 存历史实施计划与设计规格，文件名用 `YYYY-MM-DD-<主题>.md` 前缀，平铺存放，不再按日期建子目录。
- 不属于任何主题的文档：并入最接近的主题；确实无法归类的放 `misc/` 并在诊断表标注「待用户裁决」。`misc/` 是兜底目录，不是「一个文件一个目录」的许可。
- 文档旁边被引用的图片、附件等非 `.md` 资产随文档一起 `git mv`，并同步修正引用路径。
- 用 `git mv` 移动，保留历史。
- **移动前先查引用**：用 `grep -rn "<文件名>"` 全仓扫一遍，覆盖根 `README.md`、测试代码、构建与 CI 配置、其他文档；排除依赖目录、构建产物与 `.git`。移动后同步修正。
- 根 `README.md` 这类必须留在顶层的文件不要为了整齐而移动。

### 产出

移动对照表（旧路径 → 新路径），以及修正过的引用清单。

### 禁止

- 禁止不查引用就移动。
- 禁止删除历史计划或设计规格——它们进 `archive/`。
- 禁止为单个文件新建子目录。

## 阶段 2：逐篇精炼

### 要做

- 每篇位于主题目录下的活动文档开头加统一体例（索引页 `README.md` 与归档文档不套此体例）：

  ```markdown
  > **TL;DR**
  > - **用途**：这篇解决什么问题。
  > - **适用场景**：什么时候该看它。
  > - **关键结论**：读完必须知道的三五条事实、命令或红线。
  ```

- TL;DR 下面加一行 `**目录**：小节名 · 小节名 · …`，方便跳读。
- 修正可验证的过时内容：失效路径、过时数字（覆盖率门槛、任务数、端口）、已被推翻的结论。无法确认的保留原值并标注「待确认（原值：X）」。
- 一段能说清就别写三节；删掉自我重复和流水账。

### 产出

精炼后的活动文档，每篇都有 TL;DR 与目录行。

### 禁止

- 归档文档原文不动，只整理索引。
- 不改写作者原意，不补充没有依据的结论。
- 不把 TL;DR 写成正文摘要的复读——它要能替代读正文做决策。

## 阶段 3：建索引

### 要做

- `<文档根目录>/README.md` 开头不是目录树，而是「我想做什么 → 看这篇」表格，覆盖最常见的 5–10 个任务。
- 其下按主题列文档清单（文档 | 一句话内容）。
- 末尾写维护约定（见阶段 4）。
- `archive/README.md` 按日期列出计划与规格，开头声明「归档不等于废弃：排查当初为什么这么设计先来这里」。

### 产出

两份索引文件：`README.md` 的「我想做什么」表必须直接链接到每个活动文档（不依赖二次跳转，便于逐条验证）。

### 禁止

- 禁止把索引写成目录结构的罗列——读者是按任务找文档，不是按文件夹找。
- 禁止索引与实际文件不一致（至少做一次链接存在性检查）。

## 阶段 4：立长期约定

### 要做

把下面三条写进 `<文档根目录>/README.md` 的维护约定一节（项目没有这个文件就写根 `README.md`），原文可直接使用：

- **新增文档**：放进对应主题目录，并在索引页登记；不要为单个文件新建子目录。
- **改名或移动**：先全仓 `grep` 引用（根 README、测试、构建配置、其他文档），一并修正。
- **写作默认姿势**：开头先给 TL;DR（用途 / 适用场景 / 关键结论），正文再展开；一段能说清就别写三节。

若项目已有 `AGENTS.md`（或 `CLAUDE.md`）就把短版追加进去；两者都没有则跳过，不要新建。

### 产出

落盘的维护约定，以及（如适用）AGENTS.md 中的短版。

### 禁止

- 禁止只在对话里宣布规则而不落盘——下一次会话的 AI 看不到。
- 禁止把约定写成十页规范；三条足够。

## 阶段 5：验收

### 要做

- 链接检查：索引与文档中的相对链接逐个确认存在。「无断链」以检查结果 0 为准；因需改业务代码而未修的引用必须单列，不能算作通过。
- `git diff --stat` 确认只含 Markdown 与索引，没有构建产物、覆盖率报告、锁文件混入。
- 确认每篇主题目录下的活动文档都有 TL;DR。
- 确认维护约定已写入目标文件。
- 汇报：整理多少篇、归档多少篇、修正多少引用、多少未修引用、标注多少「待确认」。

### 禁止

- 不通过验收不得结束任务。
- 不得在没有实际运行检查命令的情况下声称「全部完成」。

## 红线清单

- 归档 ≠ 废弃：历史计划与设计规格只归档，不删。
- 归档原文不改写。
- 移动前必查引用。
- 不臆造事实，过时点标「待确认」。
- 不把构建产物、覆盖率报告、临时目录提交进文档树。
- 只动文档，不动业务代码。

## 验收 checklist

- [ ] 主题目录 3–7 个，取实际主题数，无凑数空目录
- [ ] 无断链（或因代码原因未修的引用已单列）
- [ ] `git diff` 只含文档与索引
- [ ] 主题目录下的活动文档均有 TL;DR 与目录行
- [ ] 索引按任务组织
- [ ] 维护约定已落盘
- [ ] 归档索引声明了「不等于废弃」

## 附：日常规范短版（可直接放进 AGENTS.md）

```markdown
## 文档约定

- 文档统一放在 `docs/`，按主题分目录：架构 / 运维 / 数据 / 测试 / 业务专题 / 评审。
- 新增文档放进对应主题目录，并在 `docs/README.md` 登记；不要为单文件新建子目录。
- 改名或移动前先全仓 grep 引用（根 README、测试、构建配置），一并修正。
- 每篇文档开头先写 TL;DR（用途 / 适用场景 / 关键结论），再写正文。
- 一段能说清就别写三节；不写没有依据的结论，不确定就标「待确认」。
- 历史实施计划与设计规格进 `docs/archive/`，原文不改，按日期命名并登记索引。
```
